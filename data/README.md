# data/

The pipeline's working directory for generated artifacts. Unlike most Python
projects, `data/` is **intentionally tracked in git, not globally ignored** — the
preference dataset this project produces is the deliverable (spec §13). See the root
[`.gitignore`](../.gitignore) for the exact policy: only `data/raw/`'s contents are
excluded (third-party datasets fetched in a later step are re-downloadable and not
worth committing), everything else under `data/` is tracked normally.

As of Stage 3, `problems/` and `candidates/` hold real artifacts; the other
subdirectories are still empty apart from a `.gitkeep` placeholder that keeps them
present in git. They
correspond 1:1 to the `paths.*` entries in [`config.yaml`](../config.yaml) and the
`Paths` dataclass in [`src/python_dpo/config.py`](../src/python_dpo/config.py), whose
`ensure_exists()` method can recreate this exact structure from scratch.

## Subdirectories

### `raw/`

Third-party datasets (e.g. HumanEval, MBPP) downloaded in a later step. Contents are
git-ignored (`data/raw/*` in `.gitignore`) since they're re-downloadable; only the
directory structure (via `.gitkeep`) is kept.

### `problems/`

**Populated (Stage 2).** `problems.jsonl` holds the ten curated Python problems that
serve as input to candidate generation — one JSON object per line, each with a prompt,
function signature, trusted reference solution, and executable tests.

Rebuild or re-check it with:

```bash
python -m python_dpo problems build      # regenerate (byte-identical if unchanged)
python -m python_dpo problems validate   # re-run every reference test, read-only
```

The file is committed deliberately: it is a project deliverable, and the build is
deterministic, so a rebuild produces no diff unless the catalog actually changed. See
[`src/python_dpo/problems/`](../src/python_dpo/problems/README.md) for the schema.

### `candidates/`

**Populated (Stage 3/4).** Candidate solutions generated by the Qwen Coder model.

- `candidates.jsonl` — the **Stage 3 legacy flat file**, kept read-only. Every candidate
  from before the Stage 4 run-directory layout, one per line. Upgrade it with
  `python -m python_dpo candidates migrate`, which reads it read-only and never modifies
  it.
- `runs/<run_id>/` — the **Stage 4 layout**. Every `generate` invocation now creates its
  own self-contained, independently auditable run directory:
  - `manifest.json` — the run's configuration snapshot and status; the source of truth
    for reproducing or resuming it (never today's `config.yaml`).
  - `candidates.jsonl` — schema 2.0: SHA-256 hashes (`code_sha256`, `prompt_sha256`,
    `raw_output_sha256`), verified on every load, plus the retry `attempt` number.
  - `failures.jsonl` — generations that produced no candidate at all. Infrastructure
    failures (`model_load`, `tokenizer`, `inference`, `timeout`) are retried per
    `generation.retry.max_attempts`; every attempt is kept as its own record.
  - `statistics.json` — always reconstructable from the two files above; never trust it
    over `candidates.jsonl`/`failures.jsonl` for anything.
  - `prompts/prompts.jsonl` — the exact prompt for every attempt, written **before**
    inference so a failed or interrupted generation still has its prompt recoverable.

Note that candidates whose code fails to parse are stored in `candidates.jsonl` with
`syntax_valid: false`, **not** in the failures file. They are the model's real output and
are exactly what later stages need on the rejected side of a preference pair.

```bash
python -m python_dpo generate --problem-id p001 --dry-run   # inspect prompts, write nothing
python -m python_dpo generate                                # a new run
python -m python_dpo generate --resume RUN_ID                 # continue an interrupted run
python -m python_dpo generate --resume RUN_ID --force          # new run seeded from RUN_ID
python -m python_dpo runs list / show RUN_ID / validate RUN_ID
python -m python_dpo candidates list / show / stats RUN_ID
python -m python_dpo candidates migrate                       # upgrade the legacy flat file
```

None of this is reproducible byte-for-byte against the **real** model: sampling with a
fixed seed is not a bit-exactness guarantee on GPU (different kernels, framework
versions, or hardware can all change the output). The deterministic mock model *is*
reproducible, which is what the automated tests assert. Run artifacts are committed as a
record of what a run actually produced, not as rebuildable artifacts.

### `evaluations/`

Results of running candidates through the (future) Docker sandbox and pytest
evaluation. Not yet populated — no execution or evaluation code exists yet (and per
`CLAUDE.md`, none will until it can run inside an isolated sandbox).

### `preferences/`

Preference pairs (chosen vs. rejected candidates) derived from evaluation results —
the DPO training input. Not yet populated — preference-pair generation is a later
step.

### `reports/`

Summaries and reports produced by pipeline runs (e.g. per-run statistics). Not yet
populated — no pipeline run exists yet.

## Files

### `.gitkeep` (in each subdirectory)

Zero-byte marker files. Git doesn't track empty directories, so each subdirectory
carries one to stay present in the repository until real content is generated.
