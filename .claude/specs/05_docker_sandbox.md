# Python DPO Data Generation Pipeline

## Step 5 — Isolated Docker Sandbox

**Specification Version:** 1.0
**Status:** Implementation Specification
**Step:** 5 of 12
**Depends On:** Step 1 — Project Skeleton
**Depends On:** Step 2 — Python Problem Dataset
**Depends On:** Step 3 — Qwen Candidate Generator
**Depends On:** Step 4 — Candidate Persistence, Runs and Reproducibility

---

# 1. Objective

Implement a secure, isolated execution environment for running untrusted Python candidate programs generated by the Qwen Coder model.

The primary objective is:

> Provide a controlled execution boundary between generated Python code and the host machine.

The sandbox will be used by later stages to execute candidate solutions against pytest test suites.

At the end of this stage, the system must be able to accept arbitrary Python source code and execute it inside an isolated Docker container while enforcing resource and security restrictions.

---

# 2. Critical Security Requirement

Generated Python code MUST be treated as untrusted.

Under no circumstances may generated candidate code execute directly on the host.

The following are explicitly prohibited:

```
exec(candidate_code)

eval(candidate_code)

subprocess.run(candidate_code)

os.system(candidate_code)

shell execution of generated code
```

The host application may use Docker commands or a Docker SDK to start containers, but the generated Python source itself must execute only inside the sandbox.

---

# 3. Scope

This stage MUST implement:

1. Docker-based sandbox.
2. Sandbox configuration.
3. Container lifecycle management.
4. Temporary execution workspace.
5. Resource limits.
6. Network isolation.
7. Filesystem isolation.
8. Non-root execution.
9. Process limits.
10. Execution timeout.
11. stdout/stderr capture.
12. Exit-code capture.
13. Structured execution results.
14. Container cleanup.
15. Sandbox health checks.
16. Security-focused tests.
17. CLI sandbox test command.
18. Mocking strategy for tests that do not require Docker.

This stage MUST NOT implement:

* pytest candidate evaluation.
* Preference generation.
* Candidate ranking.
* DPO.
* QLoRA.
* LLM judging.
* Benchmarking.
* Distributed execution.
* Kubernetes.
* Docker Swarm.
* GPU execution.
* Production orchestration.

---

# 4. Architecture

The architecture should be:

```
Candidate Code
      │
      ▼
SandboxExecutor
      │
      ▼
Temporary Job Directory
      │
      ▼
Docker Container
      │
   ┌──┴───────────────┐
   │                  │
   ▼                  ▼
candidate.py      optional test files
   │
   ▼
Python interpreter
   │
   ▼
stdout / stderr / exit code
   │
   ▼
ExecutionResult
   │
   ▼
Caller
```

The caller must never directly execute the candidate source.

# 6. SandboxExecutor

Create the primary interface:

```
SandboxExecutor
```

Conceptually:

```
result = executor.execute(
    code=candidate_code
)
```

The executor must return a structured `ExecutionResult`.

It must not return only stdout.

---

# 7. ExecutionResult

Create a typed result model containing at least:

```
status
exit_code
stdout
stderr
duration_ms
timed_out
container_id
```

Recommended additional fields:

```
error_type
error_message
signal
memory_limit_exceeded
process_limit_exceeded
network_blocked
workspace_id
created_at
```

Example:

```
{
  "status": "success",
  "exit_code": 0,
  "stdout": "42\n",
  "stderr": "",
  "duration_ms": 37,
  "timed_out": false
}
```

---

# 8. Execution Status

Use a controlled set of statuses.

At minimum:

```
success
syntax_error
runtime_error
timeout
resource_exceeded
infrastructure_error
cancelled
```

Do not classify every non-zero exit code as an infrastructure error.

For example:

```
Python raises ValueError
    ↓
runtime_error
```

while:

```
Docker daemon unavailable
    ↓
infrastructure_error
```

---

# 9. Docker Image

Use a minimal Python image.

Initial default:

```
python:3.12-slim
```

The image name must be configurable.

Example:

```
sandbox:
  image: python:3.12-slim
```

Do not use:

```
python:latest
```

because the image can change unexpectedly.

Pin the image version.

For stronger reproducibility, document the option of pinning by image digest.

---

# 10. Docker Image Requirements

The image should contain only what is required to execute Python candidate code.

Do not install:

* development tools
* compilers
* network clients
* unnecessary system packages
* SSH
* curl
* wget

unless specifically required later.

Do not install pytest yet unless the later evaluator requires it.

Step 5 should primarily establish the execution sandbox.

---

# 11. Image Preparation

Provide a documented mechanism for building or pulling the sandbox image.

For example:

```
docker pull python:3.12-slim
```

The implementation should verify that the configured image exists before attempting execution.

Provide a health-check command.

---

# 12. Network Isolation

Containers executing generated code MUST have no network access.

Use Docker network isolation:

```
--network none
```

or the equivalent Docker API configuration.

The candidate must not be able to:

* access the internet
* access localhost services
* access host network services
* perform DNS queries
* connect to external IP addresses

---

# 13. Network Security Tests

Execute a candidate attempting:

```
import socket
socket.create_connection(("8.8.8.8", 53))
```

Expected:

```
network access fails
```

Also test:

```
import urllib.request
urllib.request.urlopen("https://example.com")
```

Expected:

```
network access fails
```

Do not rely only on application-level checks.

The Docker network itself must be disabled.

---

# 14. Filesystem Isolation

The candidate must not receive access to the host filesystem.

Do NOT mount:

```
/
/home
/tmp
project directory
.git
SSH directories
cloud credentials
```

into the container.

The candidate should receive only a dedicated temporary workspace.

---

# 15. Workspace

Create an isolated temporary workspace for every execution.

Conceptually:

```
data/sandbox/jobs/<job_id>/
```

or an equivalent temporary directory.

The workspace should contain only files required for that execution.

For Step 5:

```
candidate.py
```

is sufficient.

Later stages may add:

```
test_candidate.py
```

and other controlled files.

---

# 16. Workspace Cleanup

After execution:

```
container
   ↓
stopped
   ↓
removed
   ↓
temporary workspace cleaned
```

Cleanup must occur even if:

* candidate crashes
* timeout occurs
* Docker returns an error
* Python raises an exception
* the caller receives an exception

Use appropriate cleanup/finally semantics.

---

# 17. Host Filesystem Protection

The implementation must not give the container write access to arbitrary host directories.

If a workspace is mounted, mount only the dedicated job directory.

Prefer read-only mounts where possible.

If candidate output needs to be persisted, collect it explicitly rather than exposing the project directory.

---

# 18. Read-Only Root Filesystem

Where practical, configure:

```
read_only: true
```

for the container root filesystem.

The candidate should receive a writable temporary location only if required.

If Python requires temporary filesystem access, provide a controlled temporary filesystem such as:

```
tmpfs /tmp
```

with an explicit size limit.

Document any deviation.

---

# 19. Container User

The candidate should not run as root.

Create or use a non-root user inside the sandbox image.

Example conceptual configuration:

```
user: sandbox
```

or a numeric non-root UID/GID.

Verify using:

```
os.getuid()
```

The expected result must not be:

```
0
```

---

# 20. Root Privilege Test

Run:

```
import os
print(os.getuid())
```

Expected:

```
non-zero UID
```

The test must fail if the candidate executes as root.

---

# 21. Linux Capabilities

Drop unnecessary Linux capabilities.

Prefer:

```
cap_drop = ["ALL"]
```

Do not add capabilities unless there is a demonstrated requirement.

Generated Python code does not need privileged Linux capabilities.

---

# 22. Privilege Escalation

The sandbox must not run with:

```
--privileged
```

Do not enable:

```
privileged=True
```

under any circumstances for candidate execution.

The candidate container must remain unprivileged.

---

# 23. Host Namespace Isolation

Do not use:

```
--pid=host
--network=host
--ipc=host
--uts=host
```

for candidate execution.

The container must use isolated namespaces.

---

# 24. Process Limits

A candidate can attempt to fork or spawn thousands of processes.

Configure a PID limit.

For example:

```
pids_limit = 64
```

The exact value may be configurable.

Example configuration:

```
sandbox:
  pids_limit: 64
```

---

# 25. CPU Limits

Prevent a candidate from consuming unlimited CPU.

Configure:

```
cpu_limit
```

or Docker's CPU quota controls.

Example:

```
sandbox:
  cpus: 1.0
```

Do not rely exclusively on Python-level timeouts.

Use container-level resource restrictions.

---

# 26. Memory Limits

Configure a memory limit.

Example:

```
sandbox:
  memory: "512m"
```

The exact value can be adjusted.

The candidate must not be able to consume unlimited host memory.

---

# 27. Memory + CPU Requirements

The sandbox must enforce limits at the Docker/container level.

Do not implement only:

```
if elapsed_time > timeout:
    kill()
```

Application-level timeout is necessary but insufficient.

Resource restrictions should be enforced by the container runtime.

---

# 28. Execution Timeout

Configure a hard execution timeout.

Example:

```
timeout_seconds: 5
```

The exact default can be configured.

If the candidate runs:

```
while True:
    pass
```

the sandbox must terminate it within a bounded period.

---

# 29. Timeout Behavior

When a timeout occurs:

1. Terminate the container.

2. Ensure the container is not left running.

3. Capture available stdout/stderr.

4. Return:

   status = "timeout"

5. Set:

   timed_out = true

6. Record duration.

Do not leave orphan containers.

---

# 30. Timeout Test

Execute:

```
while True:
    pass
```

Expected:

```
status = timeout
```

and:

```
container no longer exists
```

after cleanup.

---

# 31. Output Limits

A malicious candidate can print indefinitely.

The sandbox must prevent unlimited stdout/stderr accumulation.

Configure output limits.

Example:

```
max_output_bytes: 1_000_000
```

If the candidate exceeds the limit:

```
status = resource_exceeded
```

or another explicit controlled status.

Do not allow an unbounded in-memory Python string to accumulate.

---

# 32. Output Truncation

If output exceeds the configured maximum:

* truncate captured output
* record that truncation occurred
* terminate the candidate if appropriate

Example:

```
stdout_truncated: true
```

Do not silently truncate without recording it.

---

# 33. Environment Variables

Do not pass the host environment wholesale into the container.

Avoid:

```
env=os.environ
```

Pass only explicitly required environment variables.

Prefer an empty or minimal environment.

Never expose:

* cloud credentials
* API keys
* Hugging Face tokens
* SSH credentials
* database passwords

---

# 34. Secrets

The sandbox must not have access to host secrets.

Do not mount:

```
~/.aws
~/.ssh
~/.config
environment files
credential files
```

into candidate containers.

---

# 35. Docker Socket

The candidate container MUST NOT receive:

```
/var/run/docker.sock
```

Do not mount the Docker socket.

A container with access to the Docker socket can potentially control the host Docker daemon.

---

# 36. Container Lifecycle

Every execution must follow:

```
create
   ↓
start
   ↓
monitor
   ↓
collect result
   ↓
stop if necessary
   ↓
remove
```

The container must be removed after execution.

Do not leave stopped containers accumulating indefinitely.

---

# 37. Container Naming

Use deterministic-ish but unique job names.

Example:

```
python-dpo-sandbox-<run_id>-<job_id>
```

Do not rely on random names alone.

The name should help debugging.

Do not include candidate source code in container names.

---

# 38. Container ID

Store the container ID in the execution result when available.

This is useful for debugging infrastructure failures.

Do not expose container IDs unnecessarily to end users.

---

# 39. Docker Client

Use either:

* Docker CLI through a carefully controlled host-side wrapper, or
* the official Docker Python SDK.

Prefer a clean abstraction:

```
DockerContainerRuntime
```

so that the sandbox executor is not tightly coupled to a particular Docker invocation mechanism.

Do not execute candidate code through the shell.

---

# 40. Runtime Abstraction

Create:

```
ContainerRuntime
```

with operations conceptually equivalent to:

```
create()
start()
wait()
logs()
stop()
remove()
```

Then implement:

```
DockerContainerRuntime
```

This makes the executor testable without requiring Docker for every unit test.

---

# 41. Workspace Abstraction

Create:

```
SandboxWorkspace
```

Responsible for:

* creating temporary job directories
* writing candidate source
* controlling mounted files
* cleanup

It must not execute code.

---

# 42. Candidate Source File

Write the generated code to:

```
candidate.py
```

Do not dynamically inject code into a shell command.

Bad:

```
docker run ... python -c "<candidate>"
```

Preferred:

```
candidate.py
    ↓
isolated container
    ↓
python /workspace/candidate.py
```

This avoids shell quoting and injection problems.

---

# 43. Shell Invocation

Do not invoke:

```
sh -c "<candidate code>"
```

Do not interpolate candidate source into a shell command.

The command should be a fixed executable/argument list such as:

```
python
/workspace/candidate.py
```

The candidate controls only the contents of `candidate.py`.

---

# 44. Working Directory

Use a controlled working directory:

```
/workspace
```

The candidate should start execution there.

Do not use the host project directory as the working directory.

---

# 45. Python Path

Do not expose the host project's Python path.

Avoid inheriting:

```
PYTHONPATH
```

from the host.

The candidate should execute using the Python environment inside the container.

---

# 46. Host Python Packages

The candidate must not automatically see packages installed in the host virtual environment.

The container provides its own Python environment.

This is important for reproducibility.

---

# 47. Execution Command

Use a fixed command.

For example:

```
python /workspace/candidate.py
```

Do not allow the generated candidate to modify the command.

The candidate source controls only the Python program.

---

# 48. Syntax Errors

If candidate.py contains invalid Python:

```
status = syntax_error
```

Capture stderr.

Do not treat this as an infrastructure failure.

Example:

```
File "/workspace/candidate.py", line 3
    return (
          ^
SyntaxError
```

---

# 49. Runtime Errors

If the candidate executes and raises:

```
ValueError
TypeError
IndexError
...
```

return:

```
status = runtime_error
```

Capture:

```
stdout
stderr
exit_code
```

Do not crash the host application.

---

# 50. Successful Execution

For:

```
print("hello")
```

return:

```
status = success

stdout = "hello\n"

exit_code = 0
```

---

# 51. Signals

If the process terminates due to a signal, record:

```
signal
```

where available.

Classify appropriately as:

```
resource_exceeded
```

or:

```
runtime_error
```

depending on the cause.

Do not hide signal termination.

---

# 52. Environment Reproducibility

Record sandbox configuration with each execution.

At minimum:

```
image
image_digest if available
memory_limit
cpu_limit
timeout
pids_limit
network_mode
```

The later evaluation stage must be able to determine the execution environment.

# 54. Docker Availability Check

Implement:

```
python -m python_dpo sandbox health
```

It should verify:

1. Docker client is available.
2. Docker daemon is reachable.
3. Configured image is available or can be pulled.
4. A minimal sandbox container can start.
5. A minimal Python command can execute.
6. Cleanup succeeds.

Example success:

```
Docker sandbox health check passed.
```

---

# 55. Sandbox Health Failure

If Docker is unavailable, report:

```
Sandbox health check failed:
  Docker daemon is not reachable.
```

Do not produce an obscure Python traceback as the primary user-facing error.

---

# 56. CLI

Add:

```
python -m python_dpo sandbox health
```

and:

```
python -m python_dpo sandbox run --file <path>
```

The `sandbox run` command is for development/testing.

Example:

```
python -m python_dpo sandbox run --file example.py
```

It should execute the supplied file inside the sandbox.

Do not allow arbitrary host paths to be mounted into the container.

The implementation should copy the requested file into an isolated temporary workspace.

---

# 57. Sandbox CLI Security

The CLI must not execute the file directly on the host.

This is mandatory.

The command:

```
python -m python_dpo sandbox run --file candidate.py
```

must always follow:

```
host file
   ↓
isolated temporary workspace
   ↓
Docker container
   ↓
Python
```

# 76. Cleanup Verification

After every integration test:

```
docker ps
```

must not show abandoned sandbox containers.

Tests should programmatically verify cleanup where practical.

Do not depend only on manual inspection.

---

# 77. Concurrent Execution

Do NOT implement parallel sandbox execution in Step 5.

The interface should be compatible with future parallel execution, but initial implementation must execute one candidate at a time.

Parallel execution will be introduced after correctness and isolation are established.

---

# 78. Error Handling

Define explicit exceptions:

```
SandboxError
DockerUnavailableError
ContainerCreationError
ContainerExecutionError
SandboxTimeoutError
WorkspaceError
```

Do not expose raw Docker exceptions throughout the application.

Translate low-level runtime failures into meaningful application-level errors.

---

# 79. Docker Daemon Failure

If Docker stops during execution:

```
status = infrastructure_error
```

Record:

```
error_type
error_message
```

Do not classify this as candidate failure.

---

# 80. Container Creation Failure

If the container cannot be created:

```
infrastructure_error
```

No candidate correctness conclusion should be made.

---

# 81. Candidate Failure vs Infrastructure Failure

Maintain the distinction:

```
Candidate:
    syntax error
    runtime error
    timeout
    resource violation

Infrastructure:
    Docker unavailable
    image unavailable
    container creation failure
    filesystem failure
    host-side Docker API failure
```

This distinction is critical for later preference generation.

A candidate should not be marked "bad" because Docker failed.

---

# 82. No Evaluation Logic

The sandbox must not determine:

```
correct
incorrect
chosen
rejected
```

It only reports what happened during execution.

For example:

```
status = success
```

does NOT mean:

```
candidate is correct
```

It only means:

```
candidate program exited successfully.
```

Correctness will be determined in Step 6/7 by running the problem's test suite.

---

# 83. Resource Accounting

ExecutionResult should provide enough information for later evaluation to calculate:

```
execution time
timeout
resource failure
```

Record:

```
duration_ms
```

Do not use execution time as a preference signal yet.

# 85. Known Security Limitations

Document that a production-grade hostile-code execution service may require stronger isolation such as:

* microVMs
* gVisor
* Firecracker
* dedicated worker hosts
* hardened container runtimes

Do not implement those in Step 5.
