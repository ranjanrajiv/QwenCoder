**Specification Version:** 1.0
**Status:** Implementation Specification

**Depends On:** Step 1 — Project Skeleton
**Depends On:** Step 2 — Python Problem Dataset

---

# 1. Objective

Convert objectively evaluated and ranked Python candidates into high-quality preference pairs suitable for Direct Preference Optimization (DPO).

The output must contain examples of the form:

```
prompt
chosen
rejected
```

where:

```
chosen
```

is objectively better than:

```
rejected
```

according to the evaluation evidence generated by Steps 6 and 7.

The primary objective is:

> Produce high-confidence preference pairs while minimizing noisy or ambiguous DPO labels.

---

# 2. Core Principle

The DPO dataset must represent actual preference relationships supported by execution evidence.

For example:

```
Candidate A → 10/10 tests
Candidate B → 7/10 tests
```

is a valid preference:

```
A chosen
B rejected
```

But:

```
Candidate A → 10/10
Candidate B → 10/10
```

must NOT produce a preference pair.

There is no objective evidence that A is better than B.

---

# 3. Scope

This stage MUST implement:

1. Preference-pair generation.
2. Multiple configurable pair-selection policies.
3. Chosen/rejected validation.
4. Prompt reconstruction from stored artifacts.
5. Exact candidate/code deduplication.
6. Pair deduplication.
7. Minimum score-margin filtering.
8. Correctness-aware filtering.
9. Preference metadata.
10. Dataset statistics.
11. Train/validation/test splitting.
12. DPO-compatible JSONL output.
13. Dataset validation.
14. CLI commands.
15. Unit tests.
16. Integration tests.
17. Dataset quality reports.

This stage MUST NOT implement:

* DPO training.
* LoRA/QLoRA.
* model loading.
* optimizer configuration.
* reward-model training.
* candidate generation.
* candidate evaluation.
* LLM-as-a-judge.
* automatic rewriting of chosen/rejected code.

---

# 8. Canonical DPO Format

The primary DPO dataset must support the standard conceptual structure:

```
{
  "prompt": "...",
  "chosen": "...",
  "rejected": "..."
}
```

The initial implementation should also retain metadata in a separate metadata artifact.

Do not depend on training-specific metadata being accepted by every DPO trainer.

---

# 9. Recommended Dataset Separation

Create two representations.

## Training dataset

Minimal:

```
{
  "prompt": "...",
  "chosen": "...",
  "rejected": "..."
}
```

## Audit dataset

Contains:

```
preference_id
problem_id
chosen_candidate_id
rejected_candidate_id
chosen_score
rejected_score
score_margin
chosen_tests_passed
rejected_tests_passed
selection_policy
source_run_ids
...
```

This allows the DPO trainer to receive a clean dataset while preserving complete provenance.

---

# 10. Prompt

The preference prompt must come from the same problem prompt used during candidate generation.

Do not invent a new problem statement during preference construction.

The prompt should represent the programming task.

Example:

```
You are an expert Python programmer.

Solve the following problem.

Problem:
...

Required function signature:
...
```

The exact prompt should be reconstructed from the stored candidate-generation artifact.

---

# 11. Prompt Provenance

The preference pair must store:

```
prompt_sha256
```

and preferably:

```
prompt_version
```

The prompt used for both:

```
chosen
```

and:

```
rejected
```

must be identical.

A pair with different prompts is invalid.

---

# 12. Chosen Response

`chosen` must contain the candidate's actual generated Python implementation.

Do NOT:

* rewrite it
* repair it
* optimize it
* summarize it
* remove "bad" lines
* ask an LLM to improve it

The chosen response must represent what Qwen actually generated.

---

# 13. Rejected Response

`rejected` must contain the actual generated Python implementation of the rejected candidate.

Do not generate an artificial rejected answer.

The rejected implementation must be a real candidate produced by the generation stage.

---

# 14. Code Formatting

Preserve the candidate code exactly as persisted by Step 3.

Do not apply:

```
black
autopep8
ruff format
```

during preference generation.

Formatting normalization can change the training signal.

---

# 15. Code Fences

The preference dataset should use a consistent representation.

Recommended:

```
chosen = candidate.code

rejected = candidate.code
```

without Markdown code fences.

This keeps the response representation compact and consistent.

Do not re-run code extraction during Step 8.

---

# 16. Pair Validity

A preference pair is valid only when:

```
chosen_candidate_id != rejected_candidate_id
```

and:

```
chosen.code != rejected.code
```

and:

```
chosen.problem_id == rejected.problem_id
```

and:

```
chosen.prompt == rejected.prompt
```

and:

```
chosen_score > rejected_score
```

or another explicitly configured objective comparison establishes:

```
chosen > rejected
```

---

# 17. No Ties

Do NOT generate preference pairs for:

```
chosen_score == rejected_score
```

unless an explicit future preference policy introduces a secondary objective.

For Step 8 v1:

```
equal score → no pair
```

---

# 18. Correctness-Based Preference

The strongest preference is:

```
correct vs incorrect
```

Example:

```
chosen = 10/10
rejected = 8/10
```

This should be classified:

```
preference_strength = strong
```

---

# 19. Partial-vs-Partial Preference

Partial candidates may be used.

Example:

```
candidate A = 8/10
candidate B = 5/10
```

A is objectively better according to the current test suite.

This can produce:

```
chosen = A
rejected = B
```

However, the selection policy must make this configurable.

---

# 20. Recommended Default Policy

The default policy should be:

### Include

```
fully correct vs partially correct
fully correct vs completely incorrect
partially correct vs substantially worse partially correct
```

### Exclude

```
correct vs correct
equal score
indeterminate vs anything
infrastructure failure vs anything
identical code
duplicate candidate code
```

---

# 21. Score Margin

Introduce:

```
minimum_score_margin
```

Example:

```
minimum_score_margin: 0.2
```

A pair is eligible only if:

```
chosen_score - rejected_score >= minimum_score_margin
```

Example:

```
1.0 vs 0.8
```

margin:

```
0.2
```

Eligible.

Example:

```
0.8 vs 0.7
```

margin:

```
0.1
```

Not eligible under a 0.2 threshold.

---

# 22. Default Margin

The default v1 value should be:

```
0.2
```

Make this configurable.

Do not hard-code it in the pair builder.

---

# 23. Why Margin Matters

DPO labels should be high confidence.

The difference between:

```
8/10
```

and:

```
7/10
```

may be relatively weak.

The difference between:

```
10/10
```

and:

```
5/10
```

is much stronger.

The margin parameter allows experiments with preference quality.

---

# 24. Preference Policies

Implement at least these policies:

```
strict
margin
all_better
```

---

# 25. Strict Policy

The strict policy should generate pairs only when:

```
chosen = correct
```

and:

```
rejected = incorrect
```

This is the highest-confidence initial dataset.

Example:

```
10/10 vs 8/10
```

→ include

```
10/10 vs 0/10
```

→ include

```
8/10 vs 5/10
```

→ exclude

---

# 26. Margin Policy

The margin policy should allow any objectively better pair satisfying:

```
chosen_score > rejected_score
```

and:

```
score_margin >= minimum_score_margin
```

Example with margin 0.2:

```
1.0 vs 0.8 → include

0.9 vs 0.7 → include

0.8 vs 0.6 → include

0.8 vs 0.7 → exclude
```

---

# 27. All-Better Policy

The all-better policy should include every objective comparison where:

```
chosen_score > rejected_score
```

subject to:

* no ties
* no indeterminate results
* no duplicate code
* same problem
* valid provenance

This policy is useful for experimentation but should NOT be the default.

---

# 28. Policy Versioning

Every generated preference pair must record:

```
selection_policy
```

and:

```
preference_version
```

Example:

```
selection_policy: "strict"
preference_version: "v1"
```

This allows multiple datasets to be generated from the same ranking run.

---

# 29. Pair Generation

For each problem:

```
candidates = all eligible candidates
```

Generate candidate pairs:

```
C(n, 2)
```

Example:

```
5 candidates
```

produces:

```
10 possible unordered pairs
```

The pair builder evaluates each pair using the configured policy.

---

# 30. Pair Direction

For:

```
A = 10/10
B = 8/10
```

create:

```
chosen = A
rejected = B
```

Do not create both:

```
A > B
```

and:

```
B > A
```

Only one direction is valid.

---

# 31. Pair ID

Create deterministic preference IDs.

Example:

```
pref_<problem_id>_<chosen_candidate>_<rejected_candidate>
```

Example:

```
pref_p001_p001_c001_p001_c003
```

The exact format may be simplified.

The ID must be deterministic.

Do not use random UUIDs as the primary preference ID.

---

# 32. Duplicate Pair Detection

The following must be treated as duplicates:

```
A chosen / B rejected
```

appearing more than once.

Do not treat:

```
A chosen / B rejected
```

and:

```
B chosen / A rejected
```

as duplicates because the second one should be rejected as an invalid opposite preference if the scores indicate A > B.

---

# 33. Exact Code Deduplication

If:

```
chosen.code == rejected.code
```

do not create the pair.

Even if the candidate metadata differs.

Reason:

There is no meaningful response-level preference.

---

# 34. Cross-Strategy Duplicates

Candidates generated using different strategies may produce identical code.

Example:

```
normal → code A

optimized → code A
```

These must not create a preference pair against each other.

They are duplicates.

---

# 35. Cross-Run Duplicates

Candidates from different generation runs may contain identical code.

Do not automatically combine candidates from different generation runs in one ranking group.

Step 8 should operate on one selected ranking/evaluation run by default.

---

# 36. Cross-Problem Restriction

Never generate:

```
p001 candidate vs p002 candidate
```

as a preference pair.

DPO preference pairs must solve the same programming problem.

---

# 37. Problem-Level Pair Generation

The builder must group candidates by:

```
problem_id
```

before generating pairs.

This prevents accidental cross-problem comparisons.

---

# 38. Candidate Availability

If a candidate:

```
has no evaluation
```

or:

```
evaluation is indeterminate
```

it must not participate in preference generation.

Do not infer that missing evaluation means:

```
score = 0
```

---

# 39. Evaluation Run Consistency

All candidates in a preference pair must come from the same evaluation context.

At minimum:

```
same problem
same evaluation run
```

unless an explicitly configured future cross-run comparison mode is introduced.

Step 8 v1 must not compare candidates from different evaluation runs.

---

# 40. Ranking Run Consistency

The pair builder must consume one:

```
ranking_run_id
```

and use the ranking artifacts associated with it.

Do not mix rankings generated by different scoring versions.

---

# 41. Prompt Consistency

Before generating a pair verify:

```
chosen.prompt_sha256 == rejected.prompt_sha256
```

If not:

```
reject pair
```

and record:

```
invalid_prompt_match
```

---

# 42. Candidate Integrity

Before creating a pair verify:

* candidate exists
* code exists
* candidate hash matches stored code
* candidate belongs to the correct run
* candidate belongs to the correct problem

If integrity fails:

```
do not create the pair
```

---

# 43. Ranking Integrity

Before creating a pair verify:

* chosen assessment exists
* rejected assessment exists
* scores match evaluation results
* neither candidate is indeterminate
* relationship is still objectively valid

Do not blindly trust stored rank numbers.

---

# 44. Recalculate Comparison

The pair builder should call the Step 7 comparator rather than independently implementing a second scoring algorithm.

Conceptually:

```
comparison = comparator.compare(A, B)
```

Then:

```
if comparison == A_BETTER:
    candidate A may be chosen
```

This prevents ranking logic from being duplicated.

---

# 45. Preference Strength

Add:

```
preference_strength
```

Possible values:

```
strong
medium
```

For v1:

### Strong

```

```

### Medium

```
incorrect vs incorrect with sufficient score margin
```

Do not use:

```

```

in the default dataset.

# 55. Pair Generation Example

Given:

```
A = 10/10
B = 8/10
C = 10/10
D = 5/10
E = 0/10
```

Strict policy:

```
A > B
A > D
A > E
C > B
C > D
C > E
```

Do NOT generate:

```
A vs C
```

because:

```
10/10 = 10/10
```

Do NOT generate:

```
B vs D
```

under strict policy.

Do NOT generate:

```
B vs E
```

under strict policy.

---

# 56. Margin Policy Example

With:

```
minimum_score_margin = 0.2
```

Scores:

```
A = 1.0
B = 0.8
C = 1.0
D = 0.5
E = 0.0
```

Potential pairs include:

```
A > B
A > D
A > E
C > B
C > D
C > E
B > D
B > E
D > E
```

depending on the exact margin:

```
0.2
```

Pairs with:

```
margin < 0.2
```

must be excluded.

# 57. Pair Count Control

The system must support:

```
--max-pairs-per-problem
```

Example:

```
--max-pairs-per-problem 3
```

This prevents a future problem with hundreds of candidates from producing excessive pairs.

---

# 58. Pair Sampling

If the number of eligible pairs exceeds:

```
max_pairs_per_problem
```

selection must be deterministic.

Do not use uncontrolled random sampling.

If random sampling is later supported, require:

```
seed
```

and persist it in the preference manifest.

---

# 59. Pair Diversity

The pair builder should attempt to preserve candidate diversity.

Where possible, avoid generating hundreds of pairs involving only one candidate.

For example:

```
A > B
A > C
A > D
A > E
```

may dominate the dataset.

The initial implementation may preserve all valid pairs, but the architecture must allow future pair-balancing policies.

---

# 60. Candidate Strategy Metadata

The metadata artifact should preserve:

```
chosen_strategy
rejected_strategy
```

This is useful for analyzing whether certain Qwen generation strategies systematically produce better candidates.

Do not use strategy as a preference signal in v1.

---

# 61. Preference Bias Analysis

Statistics should report preference relationships by strategy where possible.

Example:

```
chosen strategy:
    normal              42%
    alternative         23%
    optimized           18%
    edge_case_focused   12%
    straightforward      5%
```

This helps identify generation-strategy bias.

Do not alter pair selection based on this statistic yet.

---

# 62. Data Leakage Prevention

The preference builder must ensure that the same exact problem does not unintentionally appear in multiple dataset splits.

This is critical.

Do NOT split individual preference pairs randomly across:

```
train
validation
test
```

if those pairs originate from the same problem.

Otherwise:

```
same problem
same prompt
different candidates
```

could appear in both training and validation.

---

# 63. Split Unit

The split unit must be:

```
problem_id
```

not:

```
preference pair
```

All preference pairs belonging to the same problem must remain in the same split.

---

# 64. Dataset Splits

Create:

```
train.jsonl

```

```

10% problems → validation
10% problems → test
```

# 65. Small Dataset Handling

The initial dataset contains only ten problems.

Therefore an 80/10/10 split produces approximately:

```
8 training problems
1 validation problem
1 test problem
```

This is acceptable for pipeline development but NOT sufficient for meaningful DPO training.

Document this explicitly.

The split mechanism must nevertheless be implemented now so that it scales to a larger dataset later.

# 69. Dataset Validation

Create:

```
PreferenceDatasetValidator
```

It must verify:

### Schema

Every record has:

```
prompt
chosen
rejected
```

### Non-empty

None of these may be empty.

### Chosen/rejected difference

```
chosen != rejected
```

### Same prompt

Chosen and rejected belong to the same problem/prompt.

### Provenance

Metadata references valid candidates.

### Objective preference

Chosen has objectively better evaluation evidence.

---

# 70. Preference Direction Validation

For every preference:

```
chosen_score > rejected_score
```

must hold for margin/all-better policies.

For strict policy:

```
chosen.correctness == correct
```

and:

```
rejected.correctness == incorrect
```

must hold.

If not:

```
validation fails.
```

---

# 71. No Reverse Pairs

If:

```
A > B
```

exists in the dataset, then:

```
B > A
```

must not exist.

The validator must detect this.

---

# 72. No Duplicate Pairs

Two identical:

```
prompt
chosen
rejected
```

records must not exist.

The validator must detect exact duplicate records.

---

# 73. Prompt Duplicate Policy

Multiple preference pairs may legitimately share the same prompt because multiple candidates solve the same problem.

Therefore:

```
same prompt
```

is NOT itself a duplicate.

The unique identity is:

```
problem + chosen + rejected
```

or the preference ID.

---

# 74. Code Duplicate Policy

If two candidates contain identical code:

```
no pair between them
```

should be created.

However, they may each participate in valid comparisons against a different candidate if policy permits.

Example:

```
A = code X, score 1.0
B = code X, score 1.0
C = code Y, score 0.5
```

Valid:

```
A > C
B > C
```

Invalid:

```
A > B
```

# 88. Testing Requirements

Create tests for:

## Strict policy

```
correct vs incorrect → include

correct vs correct → exclude

incorrect vs incorrect → exclude
```

## Margin policy

```
1.0 vs 0.8 → include with margin 0.2

0.8 vs 0.7 → exclude with margin 0.2
```

## All-better policy

```
0.9 vs 0.8 → include
```

## Ties

```
1.0 vs 1.0 → exclude
```

## Indeterminate

```
indeterminate vs correct → exclude

indeterminate vs incorrect → exclude
```

## Duplicate code

```
identical code → exclude
```

## Different problems

```
p001 vs p002 → exclude
```

## Prompt mismatch

```
different prompt → exclude
```

## Pair reversal

```
A > B and B > A → invalid
```

# 95. Chat Template Compatibility

Do not hard-code a Qwen-specific chat template in Step 8.

# 96. Candidate Response Format

For Python DPO, the preferred response is:

```
def function(...):
    ...
```

rather than:

````
```python
def function(...):
    ...
````

unless the training experiment explicitly chooses Markdown-formatted responses.

Use the same representation for chosen and rejected.

---

# 97. No Explanation Injection

Do not add:

```
"Here is the correct solution:"
```

or:

```
"This solution is better because..."
```

to the chosen response.

Do not add:

```
"This solution is incorrect because..."
```

to the rejected response.

DPO should learn from the actual candidate outputs.

---

# 98. No Label Leakage

Do not place labels such as:

```
CORRECT
INCORRECT
CHOSEN
REJECTED
```

inside the prompt or candidate response.

The preference relationship exists only in the dataset structure.

---

# 99. No Evaluation Leakage

Do not append:

```
"This solution passes 10/10 tests"
```

to the chosen response.

Do not append:

```
"This solution passes 5/10 tests"
```

to the rejected response.

The model should learn from response preference, not explicit evaluation labels.

# 105. Important Dataset Quality Principle

Do not optimize Step 8 for the maximum number of pairs.
